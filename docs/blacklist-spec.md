本文档是作者黑名单功能的产品行为、技术决策和验收标准。它会随需求和交付进度持续更新，但历史上已经交付、被替代或推迟的需求不得直接删除，应通过状态保留决策轨迹。

## 状态定义与维护规则

每项需求必须使用以下状态之一：

| 状态 | 含义 |
| --- | --- |
| `DELIVERED` | Developer 已完成实现和要求的自动化检查，且 Reviewer 已 `PASS`。该状态不表示用户已完成真实浏览器验收。 |
| `READY_FOR_DEV` | 产品行为已经确认，Developer 应在当前功能范围内实现。 |
| `IN_REVIEW` | Developer 已完成实现和自测，正在等待或进行 Reviewer 审查。 |
| `DECISION_PENDING` | 产品行为尚未确定，Developer 不得自行猜测或实现。 |
| `DEFERRED` | 已知需求，但明确不属于当前交付范围。 |
| `SUPERSEDED` | 旧行为已被其他需求取代；保留记录但不再作为目标行为。 |
| `BLOCKED` | 需求已确认，但存在必须先解决的外部依赖或技术阻塞。 |

状态维护要求：

1. Developer 只实现状态为 `READY_FOR_DEV` 的需求，不得顺带实现 `DECISION_PENDING` 或 `DEFERRED` 项。
2. Developer 完成实现和自测后，可在交接报告中建议将需求改为 `IN_REVIEW`，但不能自行标为 `DELIVERED`。
3. Reviewer 必须按需求 ID 独立审查，并报告每一项是通过、失败、不适用还是缺少证据。
4. Reviewer 对代码、自动化测试、构建、Manifest、安全性和相关快照证据给出 `PASS` 后，主协调者即可将对应需求标为 `DELIVERED`；真实浏览器验收不是该状态的前置条件。
5. 真实浏览器验收由用户负责。用户发现问题时，应新增或更新 `BUG-*` 或替代需求并标为 `READY_FOR_DEV`；原需求保留 `DELIVERED` 作为当时通过开发与审查的历史记录，不因后续浏览器反馈反复降级。
6. 只有当已交付的产品行为被新行为取代时，才将旧需求标为 `SUPERSEDED`；不得删除历史需求、Reviewer 结论或用户反馈。
7. 浏览器验收结果必须记录为用户观察，不得把源码推断或自动化结果描述为用户已验证。
8. 更新状态时必须同步更新文档版本、最后更新日期和“交付记录”。

## 产品目标

用户点击知乎首页卡片右上角的 `×` 后，不立即加入黑名单。页面先以可见的横向滑动动效，从该 `×` 左侧推出一个尽可能紧凑的小型标签抽屉；抽屉允许选择、创建和删除标签。

只有用户选择并赋予该作者一个标签后，才执行完整屏蔽流程：保存作者名称、稳定用户 ID、所选标签和首次屏蔽时间，然后隐藏该作者的卡片。当前页面中该作者的所有卡片，以及之后通过刷新、无限滚动或动态更新出现的该作者卡片，都不再显示。当前实现不包含截图或卡片图像字段，但这只是现状，不再构成默认隐私限制。

选中“拉黑该内容的点赞者”后，Cocoon 只把获取到的有效点赞者加入本地 storage 黑名单，用于插件内过滤；不得为这些点赞者调用知乎账号级拉黑接口。单作者远程拉黑选项的既有行为不变。

当前实现使用 `chrome.storage.local` 保存黑名单和标签。是否增加其他数据处理能力只按用户后续明确提出的功能需求决定，不再预设产品隐私或数据最小化限制。

当用户在知乎首页卡片底部点击“多少条评论”并展开该卡片的评论界面时，同一份 Cocoon 本地屏蔽列表也用于过滤评论：评论作者的稳定用户 ID 已存在于屏蔽列表时，该作者的评论和回复不再显示。

Cocoon 在 Chrome 扩展 Action 图标的 Badge 中显示当前标签页本次页面生命周期内实际隐藏的 Card 与评论总次数。计数只反映每个 DOM 根首次进入隐藏状态的次数，不是黑名单作者数量；刷新或重新进入页面后从零开始。

#### 已授权的真实评论 DOM 证据

用户授权连接现有登录 Chrome 中精确 `https://www.zhihu.com/` 的唯一首页标签页。检查未导航、刷新或关闭页面；为取得动态评论结构，使用当前视口内已有卡片的“数字 + 条评论”按钮打开其评论界面。按项目隐私规则，证据只保留结构、数量和字段存在性，没有记录或复述评论正文、作者名称、资料 slug、评论 `data-id` 值或其他个人标识。

真实观察结果如下：

- 评论界面以内联方式动态插入当前 `.TopstoryItem`，稳定容器类为 `.Comments-container`，本次未出现 `role="dialog"`；实现不得假设评论一定使用模态框。
- 评论列表样本包含多个 `div[data-id]` 评论根；顶层根下还可嵌套另一个 `div[data-id]` 回复根，证明每个嵌套根必须独立识别和过滤。`data-id` 只用于约束评论根结构，不得读取、记录或作为作者 ID。
- 评论容器内存在精确同源 `/people/<slug>` 作者资料链接；同一评论可能因头像和名称产生多个相同资料链接。实现必须在排除嵌套评论根后，要求当前根自身的有效资料链接无歧义，再解析稳定 `slug`。
- 评论条目周围除 `.Comments-container` 外主要使用生成式 `css-*` 类名；这些类名未记录且不得作为实现契约。可用结构契约是 `.Comments-container` 后代 `div[data-id]`、嵌套根边界和根自身精确作者资料链接的组合校验。
- 本次已真实观察评论容器由用户动作动态插入；未执行“加载更多”、切换排序或关闭后重开检查。`COMMENT-002` 对这些生命周期的要求来自已确认产品行为，Developer 必须通过动态 DOM fixture、MutationObserver 批处理测试和用户后续浏览器验收覆盖，不得把未观察部分描述为线上已验证。

`BADGE-001`～`BADGE-006` 的实现还必须满足：内容脚本可以在一个批次中合并多个新增次数以减少消息量；后台必须串行化同一标签页的 reset/increment，抵御并发消息与 Service Worker 重启，拒绝无标签页发送方、未知消息、非整数/非正增量及越界状态。`chrome.tabs.onUpdated`/`onRemoved` 如用于清理，只能读取无需 `tabs` 权限的事件参数，不得读取或持久化标签页 URL、标题或其他浏览数据。Badge 临时 storage 只保存标签页 ID、随机且不含页面语义的文档世代标识与非负计数，不进入 `cocoonBlacklistState`，不含作者、内容、URL、标题或其他页面数据；后台必须用该世代标识拒绝旧文档在刷新或导航后的迟到增量。

### Popup 与黑名单管理方案

用户已确认采用“轻量 Popup + 独立管理页”的产品方向，并授权按以下细节进入开发。Popup 的单一任务是让用户确认 Cocoon 正在工作，并快速纠正最近一次误屏蔽；完整黑名单和标签维护放在独立扩展页面，不把长列表、批量操作或复杂设置塞入点击外部即关闭的 Popup。

| ID | 状态 | 需求 |
| --- | --- | --- |
| `POPUP-001` | `DELIVERED` | Popup 顶部显示 Cocoon 名称与当前页面状态，状态至少区分“运行中”“此页面不受支持”和“页面连接异常”。“运行中”必须由当前标签页的后台临时状态与内容脚本消息共同证明，不得读取页面标题或按页面外观推断；没有当前文档临时状态时显示不受支持，有临时状态但内容脚本没有有效响应时显示连接异常。 |
| `POPUP-002` | `DELIVERED` | Popup 以“本页已拦截 N 条内容”为唯一主要视觉焦点，显示当前标签页本次页面生命周期内 Card 与评论根的准确合计；Action Badge 已显示 `999+` 时，Popup 仍显示内部准确数字。该数字继续遵守 `BADGE-001`～`BADGE-006` 的生命周期和隐私语义。 |

#### 已授权的真实页面 DOM 证据

用户已授权对现有登录 Chrome 中唯一的知乎首页进行只读检查。检查未导航、刷新或关闭页面，未记录或输出作者姓名、资料 token、成员 hash 或内容 ID。真实观察结果如下：

- 当前信息流作者触发节点可表现为 `a.UserLink-link`，其祖先结构包含 `span.UserLink.AuthorInfo-name`、`.AuthorInfo-head`、`.AuthorInfo-content` 和 `.ContentItem-meta`；作者资料链接仍提供精确 `/people/<url_token>` 稳定标识。
- 悬浮后动态创建的窗口包含稳定语义类 `.HoverCard-item`，操作区包含 `.MemberButtonGroup.ProfileButtonGroup.HoverCard-buttons`；窗口中存在唯一的精确作者资料链接，并包含知乎原有关注和私信按钮。
- 悬浮窗口外层当前使用绝对定位并具有较高层级，但其若干外层类名是生成式 `css-*`，不得作为唯一选择器。实现应从稳定的 `HoverCard` 后代结构向上定位适当窗口根，并进行尺寸、可见性和唯一作者资料链接校验。

## 已确认的技术行为

### 1. 卡片隐藏方式

采用 CSS 状态类隐藏，而不是删除节点。建议语义如下，具体类名可在实现时保持同等清晰：

```css
.cocoon-blacklisted {
  display: none !important;
}
```

选择该方式的原因：

- 不破坏知乎前端框架维护的 DOM 所有权和更新过程；
- 降低无限滚动或虚拟列表因节点被外部删除而异常的风险；
- 重复扫描可以保持幂等；
- 存储失败或未来支持解除黑名单时，可以恢复卡片；
- 调试时仍能在 DOM 中识别卡片因 Cocoon 黑名单规则而隐藏。

### 2. 作者身份

黑名单键必须是稳定的知乎作者标识，而不是作者显示名称。

当前已有证据支持以下解析来源：

1. 优先从 `/people/<url_token>` 作者资料链接读取 `url_token`；
2. 无资料链接时，从 `data-za-extra-module.card.content.author_member_hash_id` 读取成员 hash；
3. 必要时请求同源 `/api/v4/members/<hash>`，以响应中的 `url_token` 解析统一用户 ID。

存储结构应支持版本升级。v4 同时保存规范化后的 `url_token`（现有 `userId`）与可选 `memberHashId`，两者均可用于本地卡片和评论匹配；知乎账号级远程操作继续使用 `url_token`。两种标识只能来自当前 DOM 的精确资料链接、卡片 metadata 或同源成员接口的已验证映射，不能使用作者名称关联。

### 3. 持久化

黑名单存储在 `chrome.storage.local`。Manifest 只新增：

```json
"permissions": ["storage"]
```

不得为该功能新增 `tabs`、`scripting`、`<all_urls>` 或额外站点访问范围。

持久化数据必须具有显式 schema 版本。当前实现是 v4。作者记录包含以下逻辑字段，不再包含 `cardImage`：

| 字段 | 含义 |
| --- | --- |
| `userId` | 现有规范化知乎 `url_token`；用于本地匹配及需要 token 的既有行为。 |
| `memberHashId` | v4 作者记录的可空 member hash；与 `userId` 任一命中即可本地过滤，历史记录默认 `null`。 |
| `authorNameAtCapture` | 创建记录时取得的作者显示名称；仅用于记录，不得作为黑名单匹配键。 |
| `tagId` | 当前作者被赋予标签的稳定本地标识；不得只靠标签显示名称关联。 |
| `blacklistedAt` | 作者首次成功加入 Cocoon 本地黑名单时的 UTC ISO 8601 日期时间字符串；旧记录无法推断时可为 `null`。 |
| `blockSource` | 用户主动操作为 `"direct"`，点赞者本地入库为 `"upvoter"`。 |

标签集合也必须纳入显式版本化 schema。每个标签至少包含稳定本地 `tagId` 和显示名称。标签名称保存前去除首尾空白，空名称无效，最多 30 个 Unicode 字符；名称匹配不区分大小写，规范化后不得重名。作者记录通过 `tagId` 引用标签，避免标签重命名后丢失关联。

首次初始化标签存储时创建一个显示名称为 `default` 的内置标签。该标签与用户新增标签采用相同的数据结构和单选行为，不自动选中，也不会仅因打开抽屉而触发拉黑。`default` 不可删除；本轮不提供标签重命名。

用户新增标签可以删除。删除标签与迁移作者引用必须形成一次原子状态更新：先将所有引用待删除 `tagId` 的作者改为引用 `default`，再从标签集合删除该标签，最后一次性写入 `chrome.storage.local`。写入成功后才更新内存和 UI；失败时不留下部分迁移。

每名作者只保留一条记录。v4 迁移删除旧记录中的 `cardImage`、补充 `memberHashId: null` 并写回 storage，同时保留其他有效作者字段、标签和设置；迁移必须幂等。已验证的 hash alias 只能原子补写到对应 `userId` 记录，且不得与其他作者记录冲突。外部存储数据继续经过运行时校验，异常数据不得导致内容脚本停止工作。

### 4. 页面处理流程

内容脚本应遵循以下顺序：

1. 初始化时异步读取、校验并按需迁移本地黑名单；
2. 扫描已有卡片并注入按钮；
3. 对能够识别作者且命中黑名单的卡片添加隐藏类；
4. 点击 `×` 后只打开并初始化标签抽屉，保留被点击卡片作为待处理目标；
5. 用户选择已有标签或新增并选择标签；
6. 用户明确赋予标签后，解析稳定作者 ID；
7. 将无图作者记录写入本地存储；
8. 更新内存黑名单并隐藏同作者卡片和评论；
9. 若点赞者选项开启，按 `VOTER-014` 获取并写入本地点赞者记录，不发送点赞者拉黑 POST；
10. `MutationObserver` 发现新增卡片或评论后按同一身份规则过滤；
11. 所有批量 DOM 处理继续通过 `requestAnimationFrame` 分批执行。

实现必须处理初始化期间的竞态：在黑名单加载完成前扫描到的卡片，加载完成后也必须被重新判断，不能因为已经添加按钮而跳过黑名单过滤。

在用户明确赋予标签前，不得解析网络后备身份、写入作者记录、获取点赞者或隐藏卡片。任何阶段都不得执行截图或图像编码。最小作者记录写入失败时继续遵循 `ERR-001`，不得仅在内存中假装屏蔽成功。

### 5. 截图能力移除

Cocoon 不再具有截图产品需求。实现 `CAP-007` 时删除 DOM 转 Canvas、图像编码、容量预算、截图失败降级、截图错误日志和只为截图存在的第三方依赖，不得改用 Chrome API、页面 HTML、远程图片 URL 或其他方式生成替代图像，也不得新增相关权限。

## Developer 工作要求

1. 开始实现前读取本文档、`AGENTS.md`、相关源码、测试及最新本地知乎快照。
2. 在交接中列出本次实现的需求 ID，不得将未实现或未验证的 ID 声明为完成。
3. 对复杂行为继续维持既有自动化测试；纯 CSS 视觉调整不强制新增单元测试，但必须通过现有完整测试、类型检查和构建，并由 Reviewer 审查计算样式约束。
4. 不得通过删除 DOM、按作者名称匹配、扩大站点权限或引入远程服务来简化实现。
5. 运行 `npm test`、`npm run typecheck` 和 `npm run build`。
6. 需要浏览器验证时，只能按 `AGENTS.md` 规则连接用户已有 Chrome；未经用户明确允许不得执行。
7. 完成后将需求提交 Reviewer，不得自行把状态更新为 `DELIVERED`；Reviewer `PASS` 后由主协调者更新状态。

## Reviewer 工作要求

1. 独立读取本文档、`AGENTS.md`、实际 diff、源码、测试和最新本地知乎快照。
2. 按需求 ID 和验收标准逐项报告，不得只给整体印象。
3. 核实卡片使用 CSS 隐藏而不是移除，稳定 ID 匹配不会退化为名称匹配。
4. 按 `VOTER-014` 核实点赞者写入本地 storage 且没有点赞者拉黑 POST，并回归单作者远程行为不受影响。
5. 按 `CAP-007` 核实所有入口无截图、旧 `cardImage` 被迁移删除、截图代码和依赖移除且 Manifest 权限不扩大。
6. 回归 `BUG-007` 的简单悬浮窗口注入，不得恢复已被替代的复杂生命周期状态。
7. 本轮按 `CAP-007` 核实 schema v4、历史图像删除、截图代码/依赖清理；按 `BUG-008` 核实双标识直接匹配、成员接口证明、alias 原子补写、冲突/失败安全和不按名称匹配。
8. 区分自动化、快照、源码推断和用户真实浏览器观察，不得把未执行的浏览器检查写成已通过。
9. Reviewer 的 `PASS` 只基于其职责内的代码、测试、构建、Manifest、安全性和快照证据；无阻塞问题即可建议主协调者将本轮需求标为 `DELIVERED`，同时列出用户后续浏览器验收场景。
