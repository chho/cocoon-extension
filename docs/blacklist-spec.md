## 状态定义与维护规则

每项需求必须使用以下状态之一：

| 状态 | 含义 |
| --- | --- |
| `DELIVERED` | Developer 已完成实现和要求的自动化检查，且 Reviewer 已 `PASS`。该状态不表示用户已完成真实浏览器验收。 |
| `READY_FOR_DEV` | 产品行为已经确认，Developer 应在当前功能范围内实现。 |
| `IN_REVIEW` | Developer 已完成实现和自测，正在等待或进行 Reviewer 审查。 |
| `DECISION_PENDING` | 产品行为尚未确定，Developer 不得自行猜测或实现。 |
| `DEFERRED` | 已知需求，但明确不属于当前交付范围。 |
| `SUPERSEDED` | 旧行为已被其他需求取代；保留记录但不再作为目标行为。 |
| `BLOCKED` | 需求已确认，但存在必须先解决的外部依赖或技术阻塞。 |

状态维护要求：

1. Developer 只实现状态为 `READY_FOR_DEV` 的需求，不得顺带实现 `DECISION_PENDING` 或 `DEFERRED` 项。
2. Developer 完成实现和自测后，可在交接报告中建议将需求改为 `IN_REVIEW`，但不能自行标为 `DELIVERED`。
3. Reviewer 必须按需求 ID 独立审查，并报告每一项是通过、失败、不适用还是缺少证据。
4. Reviewer 对代码、自动化测试、构建、Manifest、安全性和相关快照证据给出 `PASS` 后，主协调者即可将对应需求标为 `DELIVERED`；真实浏览器验收不是该状态的前置条件。
5. 真实浏览器验收由用户负责。用户发现问题时，应新增或更新 `BUG-*` 或替代需求并标为 `READY_FOR_DEV`；原需求保留 `DELIVERED` 作为当时通过开发与审查的历史记录，不因后续浏览器反馈反复降级。
6. 只有当已交付的产品行为被新行为取代时，才将旧需求标为 `SUPERSEDED`；不得删除历史需求、Reviewer 结论或用户反馈。
7. 浏览器验收结果必须记录为用户观察，不得把源码推断或自动化结果描述为用户已验证。
8. 更新状态时必须同步更新文档版本、最后更新日期和“交付记录”。

## 产品目标

用户点击知乎首页卡片右上角的 `×` 后，不立即加入黑名单。页面先以可见的横向滑动动效，从该 `×` 左侧推出一个尽可能紧凑的小型标签抽屉；抽屉允许选择、创建和删除标签。

只有用户选择并赋予该作者一个标签后，才执行完整屏蔽流程：保存作者名称、稳定用户 ID、所选标签以及被点击卡片 `div` 的图像，然后隐藏该作者的卡片。当前页面中该作者的所有卡片，以及之后通过刷新、无限滚动或动态更新出现的该作者卡片，都不再显示。

黑名单、标签和卡片图像只保存在用户本机，不应向项目自有服务器或第三方服务上传。

## 已确认的技术行为

### 1. 卡片隐藏方式

采用 CSS 状态类隐藏，而不是删除节点。建议语义如下，具体类名可在实现时保持同等清晰：

```css
.cocoon-blacklisted {
  display: none !important;
}
```

选择该方式的原因：

- 不破坏知乎前端框架维护的 DOM 所有权和更新过程；
- 降低无限滚动或虚拟列表因节点被外部删除而异常的风险；
- 重复扫描可以保持幂等；
- 存储失败或未来支持解除黑名单时，可以恢复卡片；
- 调试时仍能在 DOM 中识别卡片因 Cocoon 黑名单规则而隐藏。

### 2. 作者身份

黑名单键必须是稳定的知乎作者标识，而不是作者显示名称。

当前已有证据支持以下解析来源：

1. 优先从 `/people/<url_token>` 作者资料链接读取 `url_token`；
2. 无资料链接时，从 `data-za-extra-module.card.content.author_member_hash_id` 读取成员 hash；
3. 必要时请求同源 `/api/v4/members/<hash>`，以响应中的 `url_token` 解析统一用户 ID。

存储结构应支持版本升级。当前建议以规范化后的 `url_token` 作为最终黑名单键；如果实现需要保存 member hash 作为解析辅助字段，必须说明用途，且不能使用作者名称作为唯一键。

### 3. 持久化

黑名单存储在 `chrome.storage.local`。Manifest 只新增：

```json
"permissions": ["storage"]
```

不得为该功能新增 `tabs`、`scripting`、`<all_urls>` 或额外站点访问范围。

持久化数据必须具有显式 schema 版本。原先只保存 `userIds` 的建议结构已不足以表达新增需求；下一版结构至少需要表达以下逻辑字段：

| 字段 | 含义 |
| --- | --- |
| `userId` | 用于黑名单匹配的稳定知乎用户 ID。 |
| `authorNameAtCapture` | 用户点击 `×` 时看到的作者显示名称；仅用于记录，不得作为黑名单匹配键。 |
| `tagId` | 当前作者被赋予标签的稳定本地标识；不得只靠标签显示名称关联。 |
| `cardImage` | 可选的 WebP Data URL、原始画布宽度和高度；仅在截图成功且未超过容量限制时存在。 |
| `blacklistedAt` | v2 新建作者首次成功加入黑名单时的 UTC ISO 8601 日期时间字符串；由 v1 迁移且无法得知历史时间的记录为 `null`。 |

标签集合也必须纳入显式版本化 schema。每个标签至少包含稳定本地 `tagId` 和显示名称。标签名称保存前去除首尾空白，空名称无效，最多 30 个 Unicode 字符；名称匹配不区分大小写，规范化后不得重名。作者记录通过 `tagId` 引用标签，避免标签重命名后丢失关联。

首次初始化标签存储时创建一个显示名称为 `default` 的内置标签。该标签与用户新增标签采用相同的数据结构和单选行为，不自动选中，也不会仅因打开抽屉而触发拉黑。`default` 不可删除；本轮不提供标签重命名。

用户新增标签可以删除。删除标签与迁移作者引用必须形成一次原子状态更新：先将所有引用待删除 `tagId` 的作者改为引用 `default`，再从标签集合删除该标签，最后一次性写入 `chrome.storage.local`。写入成功后才更新内存和 UI；失败时不留下部分迁移。

每名作者只保留一条记录和一张卡片图像；同一作者后续重复处理不得新增或覆盖已成功保存的图像。图像使用 WebP，编码质量为 `0.75`，长边不得超过 `1200` 像素。单张编码后的 Data URL 最大为 `500 KiB`，全部卡片图像的预算最大为 `5 MiB`，为 `chrome.storage.local` 的其他状态保留空间。容量按实际持久化字符串的 UTF-8 字节数计算。

图像超过单张或总预算时，不删除旧图、不覆盖旧图，也不申请 `unlimitedStorage`；改为保存不含图像的最小作者记录并继续屏蔽。具体模块边界可由 Developer 设计，但外部存储数据必须经过运行时校验，异常或旧版本数据不得导致整个内容脚本停止工作。

由于截图失败不能阻止屏蔽，持久化 schema 必须允许作者记录没有 `cardImage`，但这只能表示真实的图像采集、编码或存储失败，不得作为正常流程跳过截图。本轮不自动补采，以保持流程简单。

### 4. 页面处理流程

内容脚本应遵循以下顺序：

1. 初始化时异步读取并校验本地黑名单；
2. 扫描已有卡片并注入按钮；
3. 对能够识别作者且命中黑名单的卡片添加隐藏类；
4. 点击 `×` 后只打开并初始化标签抽屉，保留被点击卡片作为待处理目标；
5. 用户选择已有标签或新增并选择标签；
6. 用户明确赋予标签后，解析稳定作者 ID；
7. 尝试生成被点击卡片的图像；
8. 将作者名称、稳定 ID、标签和成功生成的图像一起写入本地存储；
9. 更新内存黑名单，并隐藏当前页面中该作者的全部卡片；
10. 关闭抽屉并按最终焦点规则恢复焦点；
11. `MutationObserver` 发现新增卡片后，按同一身份规则过滤；
12. 所有批量 DOM 处理继续通过 `requestAnimationFrame` 分批执行。

实现必须处理初始化期间的竞态：在黑名单加载完成前扫描到的卡片，加载完成后也必须被重新判断，不能因为已经添加按钮而跳过黑名单过滤。

在用户明确赋予标签前，不得解析网络后备身份、截图、写入作者记录或隐藏卡片。确认后的推荐事务顺序为：解析作者身份、生成 `blacklistedAt`、尝试生成卡片图像、将作者记录与标签关联、时间及成功生成的图像一并写入存储、更新内存状态、隐藏同作者全部卡片。若图像生成失败，写入不含图像的作者记录并继续屏蔽；若包含图像的存储写入因容量等原因失败，应按不含图像的记录重试一次。若最小作者记录仍写入失败，则继续遵循 `ERR-001`，不得仅在内存中假装屏蔽成功。

### 5. 卡片图像采集方案

采用 DOM 转 Canvas，并允许使用一个经过依赖审查、随扩展本地打包的 DOM 截图库，以避免自行维护复杂的 CSS/DOM 渲染器。首选 `html2canvas`；不得从 CDN 或其他远程地址加载代码，且不得再引入第二套截图实现作为常规后备。

Chrome DevTools 的“Capture node screenshot”不是可供普通扩展调用的 Chrome Extension API。`chrome.tabs.captureVisibleTab()` 只能截取可见标签页，仍需再裁剪，并要求与用户手势授权不匹配的额外权限。故本功能不采用该方案，也不新增 `tabs`、`activeTab`、`scripting`、`debugger`、`<all_urls>`、后台 service worker 或额外站点访问权限。

图像内容应来自被点击卡片 `div` 的完整当前渲染区域，并保留 Cocoon 注入的 `×` 按钮，以避免截图前临时修改 DOM。当前产品假设卡片是较短的首页缩略版，本轮不实现自动滚动、分段截图或拼接；如果真实页面证据发现卡片超出可处理范围，应按截图失败降级，但仍继续屏蔽作者。

DOM 转 Canvas 对跨域图片、复杂 CSS、视频和浏览器特有渲染的还原可能不完整。真实浏览器验证已经观察到：知乎卡片的计算样式包含 `oklch(...)`，`html2canvas@1.4.1` 会抛出 `Attempting to parse an unsupported color function "oklch"`，导致当前实现所有被测卡片截图失败。该问题记录为 `BUG-002`，必须修复，不得继续把“保存无图记录”的降级路径当作正常截图交付。

修复应保持实现和权限最小化。Developer 可优先评估升级或替换为支持现代 CSS Color 4 颜色函数的单一本地 DOM 截图库；也可在传给截图器的克隆文档中，将 `oklch()`、`oklab()` 等不支持的计算颜色转换为兼容的 `rgb()`，但不得修改用户正在浏览的真实卡片 DOM，不得新增远程代码、截图权限或并存多套常规截图方案。实现必须隔离单张卡片的转换错误，不能让截图失败中断其他卡片处理或作者屏蔽。

转换参数应限制画布长边不超过 `1200` 像素，再使用 `canvas.toDataURL("image/webp", 0.75)` 编码；若浏览器未实际产出 `image/webp` Data URL，则按截图失败处理，不再增加其他格式后备。

不得将页面 HTML、远程图片 URL 或卡片文本当作“图片”替代保存，也不得生成或保存未经裁剪的整页图像。

## 隐私与日志

- 黑名单匹配数据只使用实现本地作者匹配所需的稳定标识；作者显示名称和标签名称不得用于作者匹配。
- 屏蔽记录会额外保存点击时的作者显示名称、所选标签、首次拉黑时间和卡片图像。图像可能不可避免地包含卡片中当时可见的标题、正文摘要、头像或其他页面内容，因此应视为本地敏感数据，并遵守容量最小化原则。
- 除卡片图像中自然呈现的像素外，不得另外提取或存储卡片标题、正文、问题 ID、浏览历史、Cookie、请求头或其他无关知乎数据。
- 不得将黑名单、作者显示名称、标签或卡片图像发送到 Cocoon 自有服务器或新增第三方请求。
- Console 日志统一使用 `[Cocoon]` 前缀。
- 生产行为不应在每次过滤时输出作者真实名称或 ID；错误日志应避免无必要暴露完整黑名单。
- 本地知乎 snapshot 的读取和报告继续遵守 `AGENTS.md` 的真实个人数据规则。

## Developer 工作要求

1. 开始实现前读取本文档、`AGENTS.md`、相关源码、测试及最新本地知乎快照。
2. 在交接中列出本次实现的需求 ID，不得将未实现或未验证的 ID 声明为完成。
3. 对标签存储与规范化、标签删除和作者迁移、抽屉状态转换及动画状态、黑名单时间字段、身份匹配、去重、失败回滚、初始化竞态和 `oklch()` 截图回归编写自动化测试。
4. 不得通过删除 DOM、按作者名称匹配、扩大站点权限或引入远程服务来简化实现。
5. 运行 `npm test`、`npm run typecheck` 和 `npm run build`。
6. 需要浏览器验证时，只能按 `AGENTS.md` 规则连接用户已有 Chrome；未经用户明确允许不得执行。
7. 完成后将需求提交 Reviewer，不得自行把状态更新为 `DELIVERED`；Reviewer `PASS` 后由主协调者更新状态。

## Reviewer 工作要求

1. 独立读取本文档、`AGENTS.md`、实际 diff、源码、测试和最新本地知乎快照。
2. 按需求 ID 和验收标准逐项报告，不得只给整体印象。
3. 核实卡片使用 CSS 隐藏而不是移除，稳定 ID 匹配不会退化为名称匹配。
4. 核实点击 `×` 不会提前拉黑，并检查标签新增/选择/删除及作者迁移、抽屉动画与紧凑布局、抽屉取消、目标切换、拉黑时间、存储失败回滚、初始化竞态、动态卡片和同作者多卡片行为。
5. 核实截图修复在含 `oklch()` 的卡片上有效且没有扩大 Manifest 权限；检查第三方依赖决策、图像容量最小化和日志隐私。
6. 区分自动化、快照、源码推断和用户真实浏览器观察，不得把未执行的浏览器检查写成已通过。
7. Reviewer 的 `PASS` 只基于其职责内的代码、测试、构建、Manifest、安全性和快照证据；无阻塞问题即可建议主协调者将本轮需求标为 `DELIVERED`，同时列出用户后续浏览器验收场景。
